відкладаю, посилаючись на памʼять. **Це була неправильна причина, і я її знімаю.**

## 2. Знахідка, яка коштувала б нам 24 вересня

`bin/mkmaster.sh` **уперше дійшов до перевірки версії** — і впав:

```
241.3 + python3 -c 'import odoo; print("odoo", odoo.release.version)'
241.3 AttributeError: module 'odoo' has no attribute 'release'
ERROR: failed to build … exit code: 1
```

Причина не в майстері. **З 19.0 в офіційному образі немає
`dist-packages/odoo/__init__.py`** — `odoo` став неявним namespace-пакетом
(PEP 420). Виміряв по всіх образах, а не припустив:

```
odoo:16.0    __init__.py: є    · import odoo дає release: True
odoo:17.0    __init__.py: є    · import odoo дає release: True
odoo:18.0    __init__.py: є    · import odoo дає release: True
odoo:19.0    __init__.py: НЕМА · import odoo дає release: False
```

Тепер найважливіше. У `indexer/smoke.py` перша перевірка була

```python
python3 -c 'import OpenSSL, cryptography, lxml, psycopg2, PIL, odoo'
```

**`import odoo` для namespace-пакета успішний ЗАВЖДИ**, доки існує тека — навіть
якщо всередині немає жодного робочого файла. Тобто сторож, написаний рівно проти
зламаної платформи (той випадок 19.08, коли `cryptography` зламав `pyOpenSSL` і
кожен модуль отримував `fail` з нашої вини), **на 19.0 платформу вже не
перевіряв**, а на 20.0 не перевіряв би тим більше. Він тримався на трьох інших
імпортах; частина, що стосується Odoo, була декорацією.

Обидва місця тепер питають `from odoo import release` — справжній підмодуль,
працює і зі старою розкладкою, і з namespace-пакетом — і друкують версію:

```
   платформа: odoo 19.5a1-20260821
✓ modidx/odoo:master-deps-20260821: base ставиться, платформа ціла
```

Перевірено на обох розкладках: `16.0-deps-20260821` → `16.0-20250909`,
`19.0-deps-20260819b` → `19.0-20260817`.

Це те, для чого репетиція `master` і потрібна була: дефект у сторожі знайшовся
21 серпня, а не 24 вересня о 07:00, коли ним ніхто не займатиметься.

## 3. Перші `fail` на 16.0 — це один факт, а не п'ять

Станом на 13:54 UTC: **ok 140 · env 5 · fail 5**, у черзі 2 966.

П'ять `fail` виявилися **двома** причинами, і обидві — та сама:

```
storage        | fs_file_demo          | registry          | НЕРОЗПІЗНАНО: TypeError: unsupported operand type(s) for |
storage        | fs_attachment_s3      | py_version_syntax | fs_attachment/models/fs_file_gc.py:145 — TypeError: …
rest-framework | extendable_fastapi    | py_version_syntax | fastapi/pools/fastapi_app.py:124 — TypeError: …
rest-framework | fastapi_auth_jwt_demo | py_version_syntax | fastapi/pools/fastapi_app.py:124 — TypeError: …
storage        | fs_file_demo          | py_version_syntax | fs_attachment/models/fs_file_gc.py:145 — TypeError: …
```

`odoo:16.0` — це Debian 11 і **Python 3.9.2**. Код на гілці 16.0 містить
`batch_size: int | None = None` — PEP 604, обчислюється під час імпорту, вимагає
3.10+. Тобто модуль справді не ставиться на стандартному оточенні своєї ж серії.
Це `fail`, і він **не наш**: образ офіційний і є еталоном для 16.0, ми нічого не
знижували, у трейсбеку немає жодного пакета, який ставили ми.

Додав правило `py_version_syntax`. До нього це доходило до `registry` і виглядало
як «НЕРОЗПІЗНАНО» — тобто найтиповіша поломка серії на 3 100 модулях під 3.9 не
мала назви.

**Деталь тепер несе назву файла, і це головне в цій правці.** Дивись перший
рядок: прогін був `fs_file_demo`, а впав `fs_attachment/models/fs_file_gc.py` —
тобто **залежність**. Без файла в деталі сторінка звинувачувала б модуль у чужому
коді. `_culprit()` бере найглибший кадр трейсбеку з `/mnt/pool`: кадри самого
Odoo однакові в кожному падінні й нічого не називають.

Регресія перевірена перед вмиканням: серед **усіх** збережених `log_tail` новий
шаблон збігається рівно з одним прогоном, тобто жоден `ok`/`env`/`dep` у `fail`
не перетворюється. Статус того одного не змінився — `fail` і був `fail`, змінилися
причина й деталь.

### Питання до тебе, і я його не вирішував сам

Чотири з п'яти `fail` **заряджені модулям, чий власний код цілий**. Винуватці —
`storage/fs_attachment` і `rest-framework/fastapi` — **самі ще в черзі** й упадуть,
коли дійде черга. Тобто одна поломка дасть N рядків `fail`, і на сторінці кожного
з N написано «не ставиться», хоча ставити нічого не давав один спільний предок.

Варіанти, як я їх бачу:

1. Лишити як є. Факт правдивий: модуль не ставиться на 16.0. Деталь називає
   винуватця, отже читач не обманутий.
2. Окремий статус на кшталт `dep_broken` — «залежність присутня, але її код не
   виконується». Це нова вісь у моделі даних, і за `0010` такі рішення приймаєш ти.
3. Групувати на сторінці за винуватцем: «5 модулів не ставляться через
   `fs_attachment`».

Мій голос за 1 + 3: статус лишити, а групування зробити подачею. Але це впливає
на публічні відсотки, тому не роблю без відповіді.

## 4. Дрібне, зафіксоване, щоб не досліджувати вдруге

`declared.py` тримає маркери оточення частиною ключа, тому `pymssql` лишається в
чотирьох варіантах, а `endesive` у двох:

```
endesive<=2.18.5 ; python_version < '3.12'
endesive ; python_version >= '3.12'
pymssql<=2.2.8 ; python_version < '3.12'
pymssql<=2.2.5 ; python_version <= '3.10'
pymssql<=2.2.8 ; python_version > '3.10'
pymssql<=2.3.7 ; python_version >= '3.12'
```

Маркери **різних модулів не обов'язково взаємно виключні**: на py3.11 умови
`< '3.12'` і `> '3.10'` виконуються обидві, кожен рядок ставиться окремо, тому
перемагає останній. Вирівнювати нам нема з чого — суперечність у самих
оголошеннях OCA, а наша робота поставити те, що вендори оголосили, а не
вирішувати за них. Записано в докстрінгу `declared.py`.
