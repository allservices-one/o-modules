**C2. Розподіл `fail` за причинами, усі серії:**

```

py_version_syntax         9     9     0     0     0
sql_error                 6     1     5     0     0
registry (НЕРОЗПІЗНАНО)   5     0     5     0     0
views_xml                 4     1     1     2     0
orm_api                   2     1     1     0     0
field_removed             1     0     0     1     0
```

Плюс `warn/deprecated` 70, `dep/dep_missing_module` 3, `timeout` 1.

Найчастіша **справжня** причина на 16.0 — `py_version_syntax`: `odoo:16.0` це
Python 3.9.2, а код гілки містить `int | None` (PEP 604, потрібен 3.10+). Пʼять
`registry` на 17.0 — це наша сліпа зона, не назва причини; їх треба переглянути
поштучно перед публікацією.

**C3. Вендори.** Порахував. **І не кладу таблицю тут, свідомо.**

`ops/` — публічний репозиторій, тому «BCIM 10,8%» в outbox це вже публікація
рейтингу «хто гірший», а `CLAUDE.md` це забороняє прямим текстом. Даю форму
розподілу без імен: серед 15 вендорів із ≥40 модулями на 18.0 перенос лежить у
діапазоні **10,8% – 57,1%**, медіана близько 37%. Найбільші за обсягом (≥250
модулів) — у діапазоні 26–43%.

Порахувати з іменами може будь-хто: `modules.csv` уже містить `vendors` і
`<серія>_present`, тобто дані відкриті, а рейтинг ми не складаємо. Якщо потрібна
іменована таблиця для розуміння — скажи, і я передам її власнику приватним
каналом, не через `ops/`.

## 5. `master`: прогін у задуманому вигляді неможливий. Не запускав

Перевірив **одним модулем** перед тим, як ставити 1 178 — і добре, що так.

```
mis_builder на master: rc=0, ir_module_module.state = uninstallable
```

Причина не в коді. У повному лозі:

```
odoo.modules.module: The module website_sale_stock_available has an incompatible
version, setting installable=False        ← і так для кожного модуля пулу
```

Правило платформи, дослівно з образу
(`/usr/lib/python3/dist-packages/odoo/modules/module.py`):

```python
def check_version(version, should_raise=True):
    version = adapt_version(version)
    serie = release.major_version
    if version.startswith(serie + '.'):
        return True
```

На майстері `release.major_version == '19.5'` (`version == '19.5a1-20260821'`).
А в пулі:

```
модулів у пулі master: 1210
  префікс версії 19.0 — 1179
  префікс версії 18.0 —   31
```

**Нуль модулів пройде шлюз.** Прогін 1 178 модулів дав би 1 178 рядків
«uninstallable» через **рядок у манифесті**, а не через сумісність коду. Це не
слабша історія, це відсутність історії.

### Що я підготував і що вирішувати тобі

Готове й перевірене: `bin/mkmasterpool.sh` (пул 1 210 модулів; `var/repos/master`
— симлінк на `19.0`, бо runner монтує рівно `var/repos/<серія>`, і без цього
симлінки пулу повисли б у нікуди — той самий дефект, що спіймали 19.08),
`tmpl_master`, `series_image`, образ.

Варіанти, і всі три мають ціну:

1. **Переписувати `version` у манифесті перед прогоном** (`19.0.x` → `19.5.x`) у
   тимчасовій копії модуля. Це міряє саме те, що ти хочеш: чи працює **код** на
   лінії розробки. Але це **модифікація чужого коду**, і її треба оголосити в
   методології окремим абзацом. Технічно це перший крок будь-якої справжньої
   міграції, тому захищати таку методику можна — але це рішення про те, **що ми
   міряємо**, і воно твоє з власником, не моє.
2. **Публікувати лише платформні факти** без вердиктів по модулях: версійний шлюз
   існує, `major_version` майстра `19.5`, склад ядра 691 проти 685 на 19.0, два
   нові платформні пакети (`h11`, `pypdf`). Правда, слабко, нікого не звинувачує.
3. **Не публікувати про master нічого** і чекати справжньої 20.0.

Моя рекомендація — 1 із явним оголошенням, бо тільки вона відповідає на питання,
яке ставить читач. Але без твого «так» я чужі манифести не правлю.

### Дві твої вимоги до даних master — закриті

**Тег образу в кожному рядку.** Було відсутнє **в усьому датасеті**, не лише в
master: `modules.csv` не мав ні образу, ні дати прогону, тобто **жоден**
опублікований рядок не був відтворюваним — `status.json` називає лише *поточний*
образ серії, тому модуль, прогнаний до заміни образу, виглядав перевіреним на
образі, якого тоді не існувало. Додав `<серія>_image` і `<серія>_run_date`:

```
16.0_status  fail                              19.0_status    ok
16.0_cause   py_version_syntax                 19.0_image     modidx/odoo:19.0-deps-20260819b
16.0_image   modidx/odoo:16.0-deps-20260821    19.0_run_date  2026-08-20
16.0_run_date 2026-08-21
```

**Окрема причина для «зламала лінія розробки».** `runner.dev_line_attr()`: якщо на
19.0 **той самий `head_sha`** дав `ok`, а на master ні — різниця за побудовою
належить платформі, бо код байт-у-байт той самий. Статус `env` (у нас це «не вина
модуля», у несумісність не входить), причина `dev_line_regression`. Ознака
структурна, а не текстова — тому їй можна вірити. Обидві умови обов'язкові: без
збігу `head_sha` списувати на платформу не можна.

## 6. Дефект, знайдений сьогодні: шум `.pth` крав причину падіння

У похідних образах **18.0, 19.0 і master** `.pth`-скрипт
`extendable_pydantic_patcher` падає на старті інтерпретатора:

```
Error processing line 1 of …/extendable_pydantic_patcher.pth:
  …
  ModuleNotFoundError: No module named 'typing_extensions'
Remainder of file ignored
```

Пакет при цьому **імпортується нормально** — перевірив кодом виходу в усіх пʼяти
образах: `imports_rc=0` скрізь. Причина шуму: `.pth` виконується, коли
`/usr/lib/python3/dist-packages` ще не в `sys.path`, а constraints зробили
pip-встановлення `typing_extensions` у `/usr/local` зайвим («already satisfied»
від системного пакета).

**Ціна.** У `RULES` правило `ModuleNotFoundError: No module named …` стоїть серед
перших, а «перший збіг виграє». Тому будь-яке падіння з rc≠0 на цих образах
отримувало `env/env_missing_python: typing_extensions` замість власної причини:

```
18.0 · env · env_missing_python · 8 рядків
19.0 · env · env_missing_python · 1 рядок
```

Девʼять модулів **не були перевірені**, а в датасеті стояла вигадана причина.
Напрямок помилки важливий: `env` у несумісність не входить, тому ми не
звинувачували модулі — ми **недорахували** падіння.

`classify.py`: `PTH_NOISE` ріже блок **цілком**, від `Error processing line N of`
до `Remainder of file ignored`, а не лише слово — усередині трейсбек із
`File "…"`, `from … import` і `ModuleNotFoundError`, і будь-який рядок може
збігтися з правилом. Перевірено на справжньому лозі: шум зникає, класифікація
переходить на реальну причину. Девʼять модулів повернуто в чергу.

Образи перезбирати зараз не став: шум нешкідливий, коли класифікатор його не
читає, а перезбірка 18.0/19.0 однаково потрібна через інше — повний список
залежностей (185 назв замість 133, `outbox/2026-08-21T1325`). Зробимо разом.
