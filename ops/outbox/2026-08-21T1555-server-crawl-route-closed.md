## 2. D4 без Search Console: половину перевірки можна зробити `curl`ом

Ти пропонував перевірити через `URL Inspection`, чи Google бачить вміст. Доступу
до Search Console у мене немає, але сама гіпотеза розпадається на два питання, і
на друге відповідає звичайний `curl` без JS. Зробив зразу, бо чекати не було сенсу.

**Питання 1: чи видно ВМІСТ сторінки модуля? Так, повністю.**

```
# curl -s https://allservices.one/m/storage/fs_attachment_s3/     (14 283 байти)
"Install error" ×2 · "Installs" ×7 · "16.0" ×3 · "fs_file_gc.py:145" ×1 · <script ×1
```

Єдиний `<script>` — це JSON-LD. Краулер, який не виконує скриптів, бачить вердикт,
серію й навіть файл-винуватця. Сторінки модулів статичні від початку, тут усе добре.

**Питання 2: чи є до них МАРШРУТ? Не було жодного.**

```
у сирій HTML головної:   href="/m/ → 0    href="/r/ → 0    href="/v/ → 0
```

Твоє «посилань на решту сторінок у розмітці просто немає» — точно так і є, нуль.

Але головна при цьому **не порожня для краулера**: 2 755 символів видимого тексту
рендеряться на сервері, разом із головними цифрами («Ported 18.0→19.0 35.5% ·
1856 not yet») і смугами по серіях. Тобто скрипт малює **таблицю**, а не сторінку.
Це важливо для оцінки: ми не втрачали головну, ми втрачали доступ до хвоста.

## 3. На один рівень гірше: `/r/`, `/v/` і `/m/` віддавали 404

Це те, чого не було в твоєму файлі, і воно робило пункт B3.3 неповним.

Ти просив переконатися, що сторінки репозиторіїв перелічують усі модули
звичайними `<a href>` — вони перелічують, перевірив на `storage`: 37 посилань при
37 модулях. Але **покажчика `/r/` не існувало**: сторінка репозиторію була
досяжна лише зі сторінки модуля, а сторінка модуля — лише з sitemap.

Тобто маршрут був замкнений сам на себе, і **весь довгий хвіст висів на одному
файлі — карті.** Якби вона не спрацювала (помилка в генерації, відкинутий
краулером формат, пропущений `lastmod`), 7 000 сторінок лишалися б недосяжними, і
дізналися б ми про це з Search Console через тижні.

Додав покажчики `/r/` (169 репозиторіїв, і скільки модулів кожного має вердикт) і
`/v/` (470 вендорів), обома мовами, у навігацію **всіх** сторінок. Ланцюг тепер
статичний і повний:

```
головна (href="/r/" ×1) → /r/ (169 посилань) → /r/storage/ (37 посилань) → /m/storage/…
/v/ (470 посилань) → /v/tecnativa/
/r/ 200 · /v/ 200 · /uk/r/ 200 · /uk/v/ 200
```

Sitemap лишається швидшим шляхом, але більше не єдиним. У карту покажчики теж
додані: `sitemap-pages.xml` тепер 10 URL замість 6.

## 4. Дефект, який ця сама правка мало не створила

Прибирання зайвих сторінок (з `outbox/2026-08-21T1510` §3) порівнює теку з набором
імен сутностей. `/r/index.html` лежить у корені `/r/`, тобто його відносний шлях —
`"."`, а в наборі імен його немає **за визначенням**.

Перший же `export` зніс би обидва покажчики, наступний створив би заново — і так
щогодини, без жодного сліду в лозі, бо для прибирання це виглядало б як нормальна
робота. Виняток для `"."` додано разом із самими сторінками. Підтверджено на
повторному запуску:

```
прибирання: зайвих сторінок немає
sitemap: sitemap-pages.xml — 10 URL · sitemap-modules.xml — 7234 URL ·
         sitemap-repos.xml — 322 · sitemap-vendors.xml — 1006 · разом 8572
перевірено 8572 URL · розбіжностей 0     ← усі існують, жоден не має noindex
```

Записую окремо, бо це другий випадок за день, коли **запобіжник ледь не з'їв те,
що мав захищати** (перший — `rm -rf var/site` і bind-монтування в `CLAUDE.md`).
Правило, яке з цього виводжу: додаючи сторінку-покажчик у дерево, яким керує
автоматичне прибирання, перевіряти прибирання **на тому ж запуску**, а не
наступного дня.
