## (1) `claim()` — однорідність тепер у SQL

Замінено на вашу форму з `head`-CTE і `FOR UPDATE OF j`. Перевірка: підмішав 18.0
в голову черги так, щоб `LIMIT 8` природно захопив дві серії, і прогнав новий запит
у транзакції з `ROLLBACK`.

```
--- у голові черги (LIMIT 8) навмисно ДВІ серії:
 series | count 
--------+-------
 18.0   |     5
 19.0   |     3

--- що поверне НОВИЙ claim() з LIMIT 8:
 series 
--------
 18.0
 18.0
 18.0
 18.0
 18.0
 18.0
 18.0
 18.0
(8 rows)

UPDATE 8
--- скільки рядків лишилось у running (мусить бути рівно стільки ж):
 count 
-------
     8
ROLLBACK
```

Два числа, які тут важать: повернуто 8 і в `running` рівно 8. Старий код у цій самій
ситуації повернув би 5, а 3 задачі 19.0 лишив би в `running` назавжди. Заодно видно,
що запит **добирає** батч до повного розміру з тієї ж серії — узяв 5 пріоритетних
18.0 і ще 3 звичайних 18.0, а не обрізався на п'ятьох.

## (3) Факт установки через `ir_module_module` — і він виявився потрібнішим, ніж здавалось

`runner.py` тепер питає робочу БД **до** `drop_db`, по кожному модулю батчу.

Позитивний шлях, живий прогін:

```
$ MAX_JOBS=1 BATCH=1 python3 indexer/runner.py
воркер allservices/3644994 · BATCH=1 · MEM=2g · MAX_JOBS=1
  ✓ [19.0] stock_analytic ok/- 106092ms

 id |     module     | status | cause | latest_version | duration_ms 
----+----------------+--------+-------+----------------+-------------
 15 | stock_analytic | ok     |       | 19.0.1.0.0     |      106092
```

`latest_version` — реальні дані з бази, не з манифеста. Безкоштовно, як ви й писали.

**Негативний шлях я відтворив штучно, бо в черзі такого випадку не було.** Зібрав
модуль з `'installable': False` і прогнав повз чергу, не чіпаючи `modules` і `jobs`:

```
returncode = 0
--- лог прогону ---
... odoo.tools.config: option addons_path, invalid addons directory '/mnt/extra-addons', skipped 
... odoo.tools.config: option --without-demo: since 19.0, invalid boolean value: 'all', assume True 
... odoo.modules.module: Missing `author` key in manifest for 'probe_uninstallable', defaulting to '' 
... odoo.modules.module: Missing `license` key in manifest for 'probe_uninstallable', defaulting to LGPL-3 
--- що каже класифікатор по цьому логу (rc=0) ---
('ok', None, None)
--- що каже нова перевірка факту ---
{'probe_uninstallable': ('uninstallable', None)}
```

Це гірше, ніж «rc=0 нічого не гарантує». Тут **немає жодного сигналу в лозі**:
`invalid module names, ignored` не друкується, помилок немає, класифікатор чесно
каже `ok`. Без запиту до `ir_module_module` цей модуль назавжди пішов би в публічну
статистику як успішно встановлений. Правка закриває весь клас, а не один випадок.

Компонентна перевірка самої функції — три стани розрізняються:

```
встановлений модуль : {'base': ('installed', '19.0.1.3')}
модуля немає в БД   : {}
БД не існує         : None
```

`None` і `{}` — різні речі навмисно: `None` означає «перевірити не вдалося», і тоді
статус з логу **не** перевизначається. Інакше збій psql перетворив би весь батч на `env`.

Побічний виграш, як ви й передбачали: у батчі статуси тепер різняться по модулях,
і рядок прогону друкує по одному знаку на модуль — видно, які саме не стали,
без бісекції.

## Понад ваш список: жнець у `harvest.py`

**Без цього правка (4) не змінила б жодної цифри в БД.** `harvest.py` робив тільки
`INSERT … ON CONFLICT DO UPDATE` — він ніколи нічого не видаляв. Виправлене правило
перестало б *додавати* фантоми, але три вже наявні лишилися б у `modules` назавжди,
і `stock-logistics-transport/lessons` так і не зник би з індексу.

Жнець косить лише по парах (репозиторій, серія), які цього разу **реально прочитано**.
Для цього `handle()` тепер розрізняє «гілка без модулів» і «клон не вдався» —
без цього прапорця одна мережева помилка викосила б увесь репозиторій із індексу.
Гілка, якої вже немає в OCA, теж чиститься.

### Пастка, яку спіймав дорогою — вона стосується вас безпосередньо

Заголовок `no-store` спершу **не з'явився**, хоча `caddy validate` казав
`Valid configuration`, а `caddy reload` відпрацьовував без помилок:

```
$ stat -c '%i %s' Caddyfile
638812 7544
$ docker exec modidx-caddy stat -c '%i %s' /etc/caddy/Caddyfile
638724 7159
```

Контейнер тримав **стару копію конфігу**. Причина — `git pull --rebase`, з якого
почалася ця сесія: rebase підміняє файли робочого дерева через rename, а bind-монтування
**окремого файла** прив'язане до іноду. Тобто з 08:39 Caddy працював із конфігом,
якого на диску вже не існувало, і `reload` слухняно перечитував саме його.

Лікується `docker compose up -d --force-recreate caddy`; сертификати переживають,
вони в `var/caddy/data` (`certificate obtained` у новому лозі — 0 разів, тобто
з кешу, ліміт не витрачено).

Практичний наслідок для нашого каналу: **після кожного вашого пушу, який чіпає
`Caddyfile`, сервер мусить перевіряти інод, а не покладатися на `reload`.**
Записано в `CLAUDE.md`, розділ «Чого не робити».

## Питання, яке лишається відкритим

**11 прогонів (`runs.id` 4–14) зроблені до правки (3) і позитивного доказу установки
не мають.** Усі `ok`, з них 8 одним батчем. Зараз вони формують усю публічну

тисячами доведених і розділити їх буде вже нічим, крім `id`.
