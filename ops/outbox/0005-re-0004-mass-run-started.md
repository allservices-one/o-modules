# 0005 · R1–R3, заміри, масовий прохід — і зупинка через класифікатор

Порядок з 0004 виконаний до пункту 5. **Прохід довелося зупинити на 113-му прогоні:**
класифікація поїхала рівно так, як ви й припускали. Виправлено, прохід перезапущений.

**Головне: 5 падінь із 5 виявилися відсутніми python-пакетами в образі, а
класифікатор зараховував їх модулям як `fail`.** Тобто перша ж сотня прогонів
показала ту саму брехню, проти якої існує `classify.py`. Ваша інструкція «не чекайте
кінця, дивіться на перших сотнях» окупилася повністю.

## 1. Одинадцять прогонів видалені

Предикат ваш, не позиційний:

```
--- скільки під предикат (очікую 11):
 count 
-------
    11
--- контроль: що НЕ під предикат, лишиться:
 id | status | latest_version 
----+--------+----------------
 15 | ok     | 19.0.1.0.0
BEGIN
DELETE 11
COMMIT
```

Заодно прибрав 11 мертвих рядків `jobs.state='done'` — після B2 цей стан не
виробляється взагалі, і в черзі вони лише плутали б наступну сесію.

### R2 — «було >0, стало 0»

```
  ! жнець: sale-workflow@16.0: у БД 149, у зрізі 0 — не чіпаю
    видалено: 0 · модулів після: 8470 (мусить бути 8470)
```

Плюс `ok` гілки тепер виставляється по `rc == 0` **обох** `ls-tree`, а не лише клону.

Контроль, що жнець при цьому не паралізований:

```
--- контроль: у межах порога жнець ПРАЦЮЄ (прибираю 1 модуль) ---
    видалено: 1 · модулів після: 8469 (мусить бути 8469)
ROLLBACK — БД не змінена
```

### R3 — `method` і денний upsert

Три harvest підряд за одну добу:

```
 точок | серій 
-------+-------
     5 |     5
```

**Одне відхилення від тексту рецензії, свідоме.** Ваш індекс по `(taken_at::date)`
Postgres будувати відмовляється:

```
psql:<stdin>:88: ERROR:  functions in index expression must be marked IMMUTABLE
```

Приведення `timestamptz` до `date` залежить від параметра `TimeZone` сесії, тому не
IMMUTABLE. Зробив по `((taken_at AT TIME ZONE 'UTC')::date)` — вираз детермінований,
а доба зрізу скрізь означає добу UTC незалежно від клієнта. `ON CONFLICT` узгоджений.

## 3. Заміри на 18.0 — і `BATCH=16` провалився

**`BATCH=8`: 118,1 с на 8 модулів = 14,8 с/модуль.** Удвічі краще за ваш прогноз
25–30. Усі вісім підтверджені `ir_module_module`:

```
  ✓✓✓✓✓✓✓✓ [18.0] account_analytic_distribution_manual, account_analytic_line_commercial ok/- 118149ms
real 119.02 s
```

**`BATCH=16` у десять хвилин не вклався.** З `runs` видно, що саме сталося:
батч на 16 упав → бісекція на 8 → та вісімка теж упала → бісекція на 4 → обидві
четвірки пройшли (30 926 і 34 951 мс/модуль). Тобто великий батч не просто
повільніший — він **не проходить**, і плата за нього це два марні прогони перед
кожною успішною четвіркою.

Причина падіння лишилася невідомою, і це виявилося окремим дефектом — див. нижче.

**Висновок: `BATCH=8`.** Це вже стоїть у `modidx-runner@.service`.

## 4. Два дефекти, знайдені саме тим, що замір обірвався

Я обірвав `BATCH=16` по таймауту — і побачив те, чого не побачив би на успішному прогоні.

### Завислі задачі не поверталися ніколи

Після вбитого воркера:

```
  state  | count 
---------+-------
 queued  |  3646
 running |     8
```

`claim()` бере лише `queued`, а лок не знімав ніхто. Вісім задач зависли назавжди,
повертати довелося руками. Під systemd із `Restart=always` це не крайній випадок,
а норма: рестарт, OOM, деплой.

Додав `reclaim()`: лок, старший за 30 хвилин, повертається в чергу — на старті
воркера і далі раз на 10 хвилин. Поріг помітно більший за `RUN_TIMEOUT=420`, щоб
не забрати батч у живого воркера. Перевірено на двох локах одночасно:

```
 locked_by | count        ↺ повернуто в чергу завислих задач: 5 (лок старший за 30 хв)
-----------+-------       --- після reclaim:
 alive/1   |     3         locked_by | count 
 dead/999  |     5        -----------+-------
                           alive/1   |     3
```

Заодно прибрав осиротілу `job_d155f142f7ba` — після вбитого воркера `drop_db()`
у `finally` не відпрацював.

### Впалий батч не лишав жодного сліду

У `runs` потрапляють тільки половини після бісекції, сам упалий батч — ні. Тому
причина падіння `BATCH=16` зникла безслідно. Тепер бісекція друкує її в журнал:

```
  ↯ батч із 8 упав (rc=255, fail/registry): Реєстр не зібрався — бісекція
```

Цей рядок окупився за десять хвилин — саме він вивів на головну знахідку.

## 5. Масовий прохід: запущений, зупинений, виправлений, перезапущений

Раннери `@1` і `@2` під systemd, `BATCH=8`. Через ~20 хвилин перший зріз:

```
 series | status | count 
--------+--------+-------
 18.0   | ok     |    16
 19.0   | fail   |     4
 19.0   | ok     |    93
```

Чотири `fail`, усі з причиною `registry` — найзагальнішим правилом класифікатора.
Подивився хвіст логу:

```
odoo.modules.module.MissingDependency: External dependency 'pandas' not installed:
No package metadata was found for pandas
```

Це **не** несумісність із версією. Це відсутній пакет у нашому образі, тобто `env`.
Перевірив усі:

```
account_payroll_sheet_import       → External dependency 'pandas' not installed
account_receipt_journal            → External dependency 'openupgradelib' not installed
partner_invoicing_mode             → External dependency 'openupgradelib' not installed
partner_invoicing_mode_at_shipping → External dependency 'openupgradelib' not installed
resource_booking                   → External dependency 'cssselect' not installed
```

**П'ять із п'яти.** Весь кошик `fail` був брехнею. Прохід зупинив.

### Чому класифікатор це пропустив

Правило шукало `ModuleNotFoundError: No module named 'X'`. Але Odoo ловить
`ImportError` і піднімає **власний** `MissingDependency` з іншим текстом. Жодне
`env`-правило не збігалося, і збіг наставав аж на `Failed to load registry`
наприкінці списку — тобто на `fail`.

Формулювання взяв не з голови, а з самих образів:

```
18.0: f"External dependency {pydep} not installed: {e}"
19.0: "External dependency {dependency!r} not installed: %s"
обидва: 'Unable to find %r in path'
```

Перевірка на **справжніх збережених** `log_tail` усіх п'яти:

```
  OK  account_payroll_sheet_import        fail/registry → env/env_missing_python
      Немає зовнішнього python-пакета: pandas
  OK  account_receipt_journal             fail/registry → env/env_missing_python
      Немає зовнішнього python-пакета: openupgradelib
  ... (усі п'ять)
```

### І одразу шоста сліпа зона

Після перезапуску з'явився новий `fail/registry`:

```
Exception: Package `packaging` is required to parse `schwifty==2024.4.0`
external dependency and is not installed
```

Знову `env`. Тобто точкові патерни програють: формулювань щонайменше п'ять, вони
міняються між серіями, і про кожну наступну ми дізнавалися б уже з опублікованих
цифр. Тому додав **структурне** правило — не за текстом, а за шляхом у стеку:

```python
r"check_python_external_dependency|check_manifest_dependencies"
r"|check_external_dependencies|MissingDependency"
```

Ці функції існують рівно для перевірки `external_dependencies`, тому їхня поява в
трейсбеку однозначно означає оточення. Правило стоїть **після** точних: ті дають
назву пакета для сторінки модуля, це — гарантію, що `env` ніколи не стане `fail`.

Обидва помилкові прогони видалені й повернені в чергу.

## 8. Питання, яке варто вирішити до кінця проходу

**Чи доставляти в образ популярні python-пакети.** Зараз `openupgradelib`, `pandas`,
`cssselect`, `pycountry`, `cachetools`, `schwifty` дають `env` — статус чесний, але
модуль лишається **без вердикту**. Якщо таких виявиться помітна частка, публічна
таблиця матиме велику сіру зону саме там, де від нас чекають відповіді.

Пропоную дочекатися кінця проходу і подивитися на розподіл `env` за назвами пакетів:
якщо десяток пакетів закриває більшість, є сенс зібрати власний образ поверх
`odoo:XX` з ними — і **перепрогнати лише ті модулі**. Методологічно це чисто:
ми не змінюємо визначення сумісності, а прибираємо обмеження стенда. На сторінці
методології це треба описати окремим абзацом.

Рішення не потрібне зараз — потрібне до публікації.
