## 1. Три вісі

```
availability text NOT NULL DEFAULT 'open_source'
installable  boolean                    -- NULL = чекауту немає, не знаємо
runs.status                             -- як було
```

`indexer/state.py` — похідний `state` рахується в **одному** місці, як ви й
вимагали. Порядок перевірок не довільний:

```
absent → out_of_scope → not_verifiable → not_installable → verified → pending
```

Якби `not_installable` стояв після `verified`, модуль з `installable=false`,
колись прогнаний до введення вісі, показувався б як звичайний результат.
Перевірено на 9 межових випадках, зокрема:

```
  платний, але є прогін            → not_verifiable
  не ставиться + старий прогін     → not_installable
  манифест не розібрано            → pending          ← NULL це «не знаємо»
```

### Четвертий стан, якого не було у вашій таблиці

`out_of_scope`. 16.0 і 17.0 харнес не проганяє взагалі — чекаутів немає, у
`SERIES` їх немає. Показати їх як `pending` було б неправдою: нічого не
заплановано, і в жоден знаменник вони не входять. У `status.json` це видно:

```json
"16.0": {"out_of_scope": 3099, "total": 3099, "runnable": 0},
"17.0": {"out_of_scope": 1930, "total": 1930, "runnable": 0},
"18.0": {"pending": 2856, "verified": 16, "not_installable": 5,  "total": 2877, "runnable": 2872},
"19.0": {"verified": 596,  "pending": 565, "not_installable": 31, "total": 1192, "runnable": 1161}
```

## 2. Правило знаменника — і помилка, яку я сам зробив і зловив

Перша версія підпису казала:

```
91% of 1161 runnable modules on 19.0 (1192 total: 31 not installable, 587 pending)
```

**Це неправда.** 91% рахувався від 586 **перевірених**, а не від 1161
прогонабельних. Тобто я написав рівно ту арифметику, від якої ви застерігали —
знаменник у тексті не збігався зі знаменником у формулі. Зараз:

```
534 з 586 перевірених модулів на 19.0 встановлюються чисто (91%).
Прогонабельних: 1161 з 1192 — 31 не встановлювані за манифестом,
575 ще чекають прогону.
```

Обидва знаменники названі окремо, і жоден не підмінює інший.

`not_installable` і `not_verifiable` у `runnable` не входять — це в
`state.RUNNABLE`, одним рядком, а не розсипано по коду.

## 3. Метадані з манифестів

`indexer/manifests.py`. Без `eval` і без `import` — тільки `ast`.

**Розбираємо поключово, а не цілим літералом.** `literal_eval` на всьому файлі
падає, якщо десь є виклик чи конкатенація, і втратив би **всі** поля такого
модуля. Беремо словник як AST і обчислюємо кожне значення окремо.

```
модулів до розбору: 4069 (серії 18.0, 19.0)
готово за 6s
  ok               4069
  partial          0
  no_file          0
  failed           0
  not_installable  36
```

Жодної помилки на 4 069 манифестах.

### Вендори — те, чого ніде немає

Ваша здогадка підтвердилась: `author` майже завжди «Odoo Community Association
(OCA), <компанія>». Парасольку винесено в `is_oca`, компанії — в `vendors[]`.
Перевірка навмисно вузька: підрядок «oca» зловив би звичайні назви.

```

-------------------------+------

 Camptocamp              |   142
 Akretion                |   133
 ForgeFlow               |   112
 ACSONE SA/NV            |    97
 Gray Matter Logic       |    62

```

Це і є відповідь на «хто реально тягне екосистему», і вона готова до публікації
окремо від головної цифри.

### Гігієна екосистеми, як ви й просили порахувати

`installable: false` — **36 модулів**: 31 на 19.0, 5 на 18.0. Усі виключені з
черги; `NULL` при цьому в черзі **лишається**, бо це «манифест ще не розібрано»,
а не «не встановлюваний». Плутати ці два стани не можна — друге виключає модуль
із роботи назавжди.

`manifests.py` вбудовано в `modidx-harvest.service` **між** `sync_repos` і
`enqueue`: порядок обов'язковий, бо саме він проставляє `installable`, за яким
`enqueue` відсіює.

## 4. UI

Фільтри (категорія, вендор, стан, серія), сортування по будь-якій колонці,
групування за категорією, пошук — усе клієнтське, з одного `modules.json`
(667 КБ, Caddy віддає стисненим). 123 категорії, 138 вендорів.

**Фільтри в URL**, як ви й наполягали:

```
/?cat=Accounting%20%26%20Finance&vendor=Tecnativa&state=fail&series=19.0&group=1&sort=v:desc
```

Картка модуля посилається **назад** у відфільтрований список — зв'язок працює в
обидва боки: з таблиці в модуль і з модуля в «усі модулі цього вендора».
`canonical` завжди на чисту адресу.

Віконна відмальовка по 200 рядків. Напрямок сортування — стрілкою і `aria-sort`,
не кольором. Статуси лишаються іконкою з підписом.

### Перевірено виконанням, а не переглядом

Синтаксису мало, тому справжній **згенерований** скрипт прогнано в node із
заглушками DOM проти справжнього `modules.json`:

```
  без фільтрів                       → 4447 рядків з 4447
  категорія Accounting               → 128 рядків з 4447
  вендор Tecnativa                   → 732 рядків з 4447
  стан not_installable               → 36 рядків з 4447
  перевірені на 19.0                 → 586 рядків з 4447
  Tecnativa, перевірені 19.0         → 173 рядків з 4447
  пошук account                      → 618 рядків з 4447
```

`not_installable` дає рівно 36 як у БД, `verified` на 19.0 — 586 як у підписі
під смугою. Комбінації складаються.
