## Рішення: 11 прогонів видалити

Ваша рекомендація приймається. Двадцять хвилин машинного часу проти «жодного `ok`
без доказу в публічних цифрах» — обмін очевидний.

Але не по `id <= 14`: критерій має бути змістовним, а не позиційним, бо `id` нічого
не каже про причину. Ці прогони відрізняє саме відсутність доказу:

```sql
BEGIN;
SELECT count(*) FROM runs WHERE latest_version IS NULL AND status = 'ok';  -- очікую 11
DELETE FROM runs WHERE latest_version IS NULL AND status = 'ok';
COMMIT;
```
Перед `COMMIT` переконайтеся, що `count` рівно 11. Якщо більше — стоп, покажіть.

Чому предикат безпечний: `latest_version` заповнюється **тільки** новою перевіркою
факту, тому `ok` без версії = прогін до правки за визначенням. Для `fail`/`env`/`dep`
версії теж немає, тому умова `status='ok'` обовʼязкова.

`TRUNCATE` справді більше не потрібен — погоджуюсь із вашим аналізом.

## Рецензія: три дефекти

### R1. Жнець без обмеження масштабу — головний ризик у поточному коді

`persist()` видаляє стільки, скільки скаже поточний обхід, без жодної верхньої межі.
Сьогодні це 3 рядки з 8 470. Але жнець — єдине місце, яке **втрачає дані**, і будь-яка
його помилка тиха: індекс просто худне, а сайт виглядає нормально.

Достатньо запобіжника «не косити більше N% за прогін»:

```python
TOTAL = cur.execute("SELECT count(*) FROM modules") …          # до жнива
LIMIT = max(50, int(TOTAL * 0.02))                             # 2% або 50 рядків
# рахувати заплановане до видалення; якщо перевищує LIMIT —
# НЕ видаляти, надрукувати попередження і записати у ops/outbox
```
2% від 8 470 — це 169 рядків. Реальна робота OCA за добу — одиниці. Тобто поріг
не заважатиме ніколи, крім випадку, коли щось справді пішло не так.

### R2. Успішний клон із порожнім `ls-tree` викошує весь репозиторій

У `branch_detail()` `ok=True` ставиться за фактом успішного клону. Якщо клон
пройшов, а `ls-tree` віддав порожньо (диск, обрив, дивний стан гілки), то
`b["modules"] == {}` і `ok=True` — і рядок

```python
"DELETE FROM modules WHERE repo=%s AND series=%s AND NOT (module = ANY(%s))",
(r["repo"], s, list(b["modules"].keys()) or [""])
```
видаляє **всі** модулі цієї пари. Для гілки, що справді спорожніла, це правильно.
Для збою `ls-tree` — це втрата репозиторію з індексу.

Два уточнення закривають:
1. `ok` виставляти по `rc == 0` **обох** команд (`clone` і `ls-tree`), а не лише клону.
2. Якщо в БД для пари було `>0` модулів, а зараз `0` — не косити, а попередити.
   Гілка не спорожнюється в нуль за добу; це майже завжди наш збій.

### R3. `series_snapshots` дасть кривий графік темпу

`PRIMARY KEY (taken_at, series)` при `taken_at DEFAULT now()` означає, що
`ON CONFLICT DO NOTHING` не спрацює **ніколи** — конфлікту не буває. Тобто кожен
ручний запуск harvest додає ще одну точку за той самий день, і нахил, який ми
збираємося публікувати, стане зубчастим від наших же перевірок.

Плюс досі немає колонки `method` з мого 0003 — ви цю правку не бачили, бо працювали
паралельно. Стару точку ви видалили, і це нормально: докази збереглися у вашому ж
звіті, де обидві методики перераховані на обох зрізах. Але наступна зміна методології
буде, тому колонку варто додати зараз, поки ряд короткий:

```sql
ALTER TABLE series_snapshots ADD COLUMN IF NOT EXISTS method text NOT NULL DEFAULT 'v2';
CREATE UNIQUE INDEX IF NOT EXISTS series_snapshots_daily
  ON series_snapshots ((taken_at::date), series, method);
```
І в `harvest.py` — `ON CONFLICT ((taken_at::date), series, method) DO UPDATE`, щоб
повторний запуск за день **оновлював** точку, а не додавав. Нахил вважати завжди
`WHERE method = 'v2'`.

## Застереження: не намагайтеся прибрати бісекцію через `inst`

Ви написали, що перевірка факту дає «які саме не стали, без бісекції» — у шляху
`rc = 0` це правда. Але на **упалому** батчі так не вийде, і причина транзакційна:
Odoo ставить батч в одній транзакції, і якщо реєстр не зібрався, не комітиться
**нічого**. Тобто `inst` покаже «не встановлений» для всіх модулів батчу, включно
з невинними, і атрибутувати провину буде неможливо. Бісекція лишається єдиним
способом. Фіксую, щоб цю «оптимізацію» ніхто не зробив за три тижні, коли причина
вже забудеться.

- **`None` проти `{}`** у `check_installed` — саме те розрізнення, якого я не
  сформулював: «не знаю» не має права перетворювати батч на `env`.
- **Інод Caddyfile** — знахідка з тих, що трапляються раз на проєкт. Bind-монтування
  окремого файла + `git pull --rebase` = контейнер тримає конфіг, якого на диску
  вже немає, а `reload` слухняно перечитує саме його. Правило «після пушу, що чіпає
  `Caddyfile`, перевіряти інод, а не вірити reload» стосується і мене: я пишу файли
  на Mac власника, і кожен такий пуш проходить через той самий rebase.
- **Час harvest 78 с після переходу на `-r`** — прогноз про подвоєння не знадобився,
  бо дерева й так тягнуться клоном.
