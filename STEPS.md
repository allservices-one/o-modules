## ЕТАП B. Аудит сервера. Нічого не змінюємо (30–60 хв)

### 5. Перший промпт у сесії на сервері
Скопіюйте дослівно:

> Прочитай CLAUDE.md. Це аудит, режим тільки-читання: **нічого не змінюй, не встановлюй,
> не перезапускай і не редагуй конфіги.** Спершу виконай `bash bin/preflight.sh > /root/pf.txt`
> і покажи вивід. Далі склади звіт по сервері за пунктами:
> 1. ОС, ядро, віртуалізація, cgroup v2, vCPU/RAM/swap, диск і inode.
> 2. Що слухає 80, 443, 5432 і будь-які інші відкриті порти — процес, юніт, шлях до конфігу.
> 3. Який саме ресурс зараз працює на allservices.one: що це за застосунок, стек,
>    де його файли, які URL-шляхи він обслуговує, чи є в нього БД і де вона.
> 4. Чи ним хтось користується: подивись логи доступу за останні 7 днів — скільки запитів,
>    які шляхи найчастіші, чи є звернення до API, чи є не-браузерні клієнти.
> 5. Що в crontab (усіх користувачів), які enabled systemd-юніти нестандартні, чи є docker
>    і що в ньому.
> 6. Чи є бекапи цього ресурсу і де вони.
> 7. Сертификати: чим видані, коли протермінуються, чи є certbot.
> 8. DNS: A, AAAA, MX, TXT для apex і www. Окремо скажи, чи AAAA веде на цей сервер.
> 9. Ризики: що зламається, якщо перевести цей ресурс з апексу на субдомен.
>
> У кінці — список рішень, які я мушу ухвалити, з твоєю рекомендацією по кожному.

### 6. СТОП-ТОЧКА 1

## ЕТАП C. Рішення після аудиту (той же день)

### 7. Ім'я субдомену для наявного ресурсу
Обрати одне: `app.`, `old.`, `panel.` — залежно від того, що це за ресурс.

### 8. Чи можна рухати апекс
Якщо аудит покаже, що до апексу звертаються машинні клієнти або в нього вшиті інтеграції —
або лишаємо старий ресурс на апексі й беремо для індексу субдомен, або робимо 301 і живемо
з ними довго. Це рішення ваше, я дам розклад наслідків.

### 9. Бекап перед будь-якими змінами
```bash
D=/root/backup-$(date +%F) && mkdir -p $D
cp -a /etc/nginx $D/ 2>/dev/null; cp -a /etc/apache2 $D/ 2>/dev/null
cp -a /etc/caddy $D/ 2>/dev/null
crontab -l > $D/crontab-root.txt 2>/dev/null
systemctl list-unit-files --state=enabled > $D/units.txt
docker ps -a > $D/docker.txt 2>/dev/null
# і дамп БД старого ресурсу, якщо вона є — команду дасть сесія на сервері
tar czf $D.tar.gz $D && ls -la $D.tar.gz
```

### 10. DNS
- Додати A (і AAAA, якщо є IPv6 цього сервера) для обраного субдомену → **цей сервер**.
- Привести AAAA апекса в порядок: або видалити, або переставити на цей сервер.
- TTL зменшити до 300 с **за годину до** перемикання, щоб відкат був швидким.

### 11. СТОП-ТОЧКА 2
Дочекатися, поки DNS розійдеться. Перевірка з мого боку: скажіть — я подивлюсь, куди
резолвиться субдомен і апекс, і чи не лишилось «хвоста» на старому IPv6.

## ЕТАП D. Перенесення ресурсу і підняття Caddy (1–2 години)

### 12. Наявний веб-сервер → на внутрішній порт
Перевести його слухати `127.0.0.1:8080` (не `0.0.0.0`), перезапустити, переконатися,
що `curl -I http://127.0.0.1:8080/` відповідає. 80 і 443 мають звільнитися.

### 13. Caddy зі staging-сертификатом
У `Caddyfile` розкоментувати блок `acme_ca … staging`, підставити реальний субдомен,
підняти:
```bash
cd /srv/modidx && docker compose up -d caddy && docker compose logs -f caddy
```
Мета цього кроку — переконатися, що ACME-виклик проходить, не витрачаючи ліміт
справжніх сертификатів.

### 14. Перемикання на справжній сертификат
Закоментувати staging, `docker compose restart caddy`, перевірити обидва хости.

### 15. Редиректи старих шляхів
Вписати реальні префікси старого ресурсу в блок `redir … permanent` на апексі.
Перелік префіксів бере сесія на сервері з логів доступу (пункт 5.4).

### 16. СТОП-ТОЧКА 3
Скажіть мені — я з цього боку перевірю зовні: сертификат і ланцюжок, заголовки,
чи працює субдомен, чи 301 ведуть куди треба, чи нічого не загубилось.

## ЕТАП E. Індексатор (2–3 години активної роботи, далі само)

### 17. Bootstrap
```bash
cd /srv/modidx && ROOT=/srv/modidx bash bin/bootstrap.sh
```
Ставить swap 4 GB, теки, ліміти логів Docker, Postgres із tuned-конфігом, схему,
шаблонні БД для 18.0 і 19.0. Ідемпотентний — можна повторювати.

### 18. Перший зріз OCA
```bash
python3 indexer/harvest.py
```
~2 хвилини. **Контроль:** цифри мають зійтися з `CLAUDE.md` (19.0 ≈ 1103 модулі,
20.0 = 0 гілок) з поправкою на кілька днів. Якщо ні — щось не так із мережею або списком репо.

### 19. Чекаути й пул адонів
```bash
bash bin/sync_repos.sh
```
~6 GB, 10–20 хвилин. Наприкінці друкує, скільки модулів у пулі кожної серії.

### 20. Один прогін вручну — найважливіша перевірка
```bash
python3 indexer/enqueue.py
BATCH=1 python3 indexer/runner.py
```
Дивимось, що модуль реально ставиться в контейнері, лог парситься, статус пишеться в БД.
**Тут майже напевно буде правка** — це перший живий запуск `runner.py`. Сесія на сервері
має її зробити й показати, що змінила.

### 21. Заміряти реальну швидкість
Після 20–30 прогонів: середній час одного, і перерахувати, скільки триватиме повний прохід.
Якщо більше 60 с на модуль — розбиратися, де вузьке місце, до масового запуску.

### 22. Під systemd, два воркери, батчі
```bash
cp systemd/*.service systemd/*.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now modidx-runner@1 modidx-runner@2
systemctl enable --now modidx-harvest.timer modidx-export.timer modidx-maint.timer
watch -n5 'free -m; docker ps --format "{{.Names}} {{.Status}}"'
```
Подивитися 10 хвилин на память. **Третій воркер не додавати.**

### 23. СТОП-ТОЧКА 4
Надішліть:
```bash
docker exec -it modidx-pg psql -U odoo -d modidx -c \
 "SELECT series, status, count(*) FROM latest_runs GROUP BY 1,2 ORDER BY 1,2;"
```
Це перша в світі таблиця фактичної сумісності модулів OCA. Дивимось разом, чи класифікація
адекватна — саме тут вирішується, чи цифрам можна вірити.

## Точка go / no-go — 30 листопада
- 1 000 унікальних відвідувачів-партнерів за 60 днів
- 100 безкоштовних watchlist-акаунтів
- 10 платних підписок (~$390 MRR)

Менше 5 платних — партнери не купують інформацію, вони купують роботу. Тоді індекс
залишається безкоштовним лідгеном, а гроші переходять у платну міграцію модулів.

## Що робити, якщо щось пішло не так

| Симптом | Перше, що перевірити |
|---|---|
| Caddy не бере сертификат | AAAA веде на інший хост; порт 80 зайнятий; ліміт Let's Encrypt |
| Старий ресурс віддає 502 | він не слухає `127.0.0.1:8080` або слухає лише зовнішній інтерфейс |
| OOM, воркер убитий | працює третій воркер; немає swap; `--memory` не застосувався (cgroup v1) |
| Прогін довше 2 хв | немає шаблонної БД, ставиться `base` щоразу |
| Усі модулі у статусі `env` | немає python-залежностей в образі — це не несумісність, класифікатор правий |
| Диск заповнився | `var/repos` на кілька серій; прибрати 16.0/17.0, `docker image prune` |
| Цифри harvest не збігаються | список репо застарів (`var/oca_repos.txt`) — видалити, він перезбереться |
