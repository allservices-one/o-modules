## ЕТАП C. Передумови сервера (10 хв) ✅

### 7. Swap і ліміт журналу
Обидві передумови були відсутні й закриті 19.08.2026 перед bootstrap:

```bash
# swap 4 GB — тим самим способом, що й bootstrap.sh, щоб він потім пропустив крок
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap -q /swapfile && swapon /swapfile
grep -q '^/swapfile' /etc/fstab || echo '/swapfile none swap sw 0 0' >> /etc/fstab
sysctl -qw vm.swappiness=10
grep -q 'vm.swappiness' /etc/sysctl.conf || echo 'vm.swappiness=10' >> /etc/sysctl.conf

# ліміт journald — було 3,6 GB без SystemMaxUse при бюджеті 3 GB на всі логи
mkdir -p /etc/systemd/journald.conf.d
printf '[Journal]\nSystemMaxUse=500M\nSystemMaxFileSize=50M\n' \
  > /etc/systemd/journald.conf.d/modidx.conf
systemctl restart systemd-journald && journalctl --vacuum-size=500M

# контроль
free -h && swapon --show && journalctl --disk-usage
```

Результат: swap 4,0 Gi активний, journald 3,5 G → 457 M, `/var/log` 3,9 G → 780 M.

Без swap перший же `BATCH=8` із двома контейнерами Odoo впритул до 7,6 GB RAM — це OOM,
а не сповільнення.

## ЕТАП F. Домен і Caddy — ЗАБЛОКОВАНО на AAAA ⏸

**Нічого з цього етапу не робити, поки власник не виправить AAAA.** Кожна невдала спроба
витрачає ліміт Let's Encrypt: 5 невдач на домен за годину.

### 18. Дочекатися AAAA
Потрібно, щоб AAAA апекса й www або **зникли**, або показували на IPv6 цього сервера:

```bash
dig +short AAAA allservices.one       # має бути порожньо або 2a01:4f9:c012:c08a::1
dig +short AAAA www.allservices.one   # те саме
dig +short A    allservices.one       # 65.21.189.197 — уже правильно
```

Зараз там `2001:41d0:203:dee4:5:39:10:93` — паркувальний сервер Imena.UA у мережі OVH.
ACME піде по IPv6 туди, токена не знайде, сертификата не видасть.

**У DNS чіпати тільки AAAA.** `MX 10 mail.imena.com.ua` — робоча пошта домену.
TXT `google-site-verification` — підтвердження власності в Search Console. Обидва лишити.

Заодно попросити прибрати: `monitor.allservices.one` і `gitlab.allservices.one`
(A на цей сервер, висять мертвими) і 13-байтну заглушку `176.36.160.43` на паркуванні —
вона публічно віддає домашню IP-адресу власника кожному, хто зробить IPv6-запит.

### 19. Caddy зі staging-сертификатом
Спершу перевірити конфіг, не піднімаючи сервер:
```bash
cd /srv/modidx
docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile
```
Потім у `Caddyfile` розкоментувати глобальний блок `acme_ca … staging` і підняти:
```bash
docker compose up -d caddy && docker compose logs -f caddy
```
Мета кроку — переконатися, що ACME-виклик проходить, не витрачаючи ліміт справжніх
сертификатів.

### 20. Перемикання на справжній сертификат
Закоментувати staging, `docker compose restart caddy`, перевірити апекс і www.

### 21. Перевірити 410 на старих шляхах
Блок `@gone` у `Caddyfile` уже написаний — префікси взяті з
`archive-allservices-2026-08-18/meta/top-2000-urls.txt`. Перевірити, що віддається саме
410, а не 404 і не 200:
```bash
for p in /shop/category/foo /web/image/website/1/logo /en/ /website/translations \
         /website_sale/get_combination_info; do
  printf '%-42s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://allservices.one$p)"
done
# і контроль, що новий сайт не зачепило:
for p in / /methodology.html /modules.json /llms.txt /data/modules.csv; do
  printf '%-42s %s\n' "$p" "$(curl -s -o /dev/null -w '%{http_code}' https://allservices.one$p)"
done
```
Перші п'ять — `410`. Другі п'ять — `200`.

## ЕТАП H. Вересень — технічна частина

### 26. Лінія розробки до релізу
`master` = версія 19.5-alpha (`odoo/release.py`), нічні збірки на
`nightly.odoo.com/master/nightly/deb/`. Образ будувати з **датованого** .deb
(`modidx/odoo:master-YYYYMMDD`), ключ серії в БД — `master`, ніколи `20.0`.
Результати `master` не входять у головні відсотки й не публікуються як «Odoo 20».

### 27. 24 вересня, день кейноуту
Гілки `20.0` починають з'являтися в публічному git. Того ж дня: образ у харнес, гілка в
`sync_repos.sh`, прогін. Офіційного образу `odoo:20.0` може не бути — для 19.0 тег
з'явився наступного дня після кейноуту, для 18.0 через два тижні. Тому ім'я образу
мусить бути параметром, а не константою в коді.

## Що робити, якщо щось пішло не так

| Симптом | Перше, що перевірити |
|---|---|
| Caddy не бере сертификат | **AAAA апекса** — перша й найімовірніша причина тут; ліміт Let's Encrypt (5 невдач/год); порт 80 |
| Старі URL віддають 404, а не 410 | префікс не потрапив у `@gone`; `handle` блоки взаємовиключні — перевірити, що `file_server` у своєму `handle` |
| Сайт раптом весь 404, хоча файли на місці | `rm -rf var/site` при живому Caddy ламає bind-монтування: контейнер тримає видалений inode. Лікується `docker compose restart caddy`. Чистити вміст, а не теку: `rm -rf var/site/*` |
| Новий сайт віддає 410 | шлях нового сайту зачепив `@gone`; новий сайт займає `/`, `/m/*`, `/r/*`, `/data/*`, `/modules.json`, `/llms.txt`, `/methodology.html` — перетинів бути не має |
| OOM, воркер убитий | працює третій воркер; `swapon --show` порожній; `--memory` не застосувався (cgroup v1) |
| Прогін довше 2 хв | немає шаблонної БД, ставиться `base` щоразу |
| Усі модулі у статусі `env` | немає python-залежностей в образі — це не несумісність, класифікатор правий |
| Диск заповнився | `var/repos` на кілька серій; прибрати 16.0/17.0, `docker image prune`; журнал — `journalctl --disk-usage` |
| Цифри harvest не збігаються | список репо (`data/oca_repos.txt`) — **не видаляти**; подивитись у лозі harvest рядки `+ новий репозиторій` / `− зник` і чи не спрацював поріг дрейфу |
| `git push` — Permission denied | deploy key ще не доданий, `GIT.md` крок 4. Комітити локально, не пушити |
