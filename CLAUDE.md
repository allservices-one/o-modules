# Module Health Index — контекст проєкту

Цей файл читає Claude Code, коли запускається в `/srv/modidx`. Тут усе, що потрібно знати,
щоб не перевиводити висновки заново.

## Що це

Публічний індекс **фактичної** сумісності модулів Odoo з версіями Odoo. Не заяви вендорів,
а результат реального `docker run odoo -i <module>` у чистій базі кожної серії.

Приватний проєкт однієї людини. Не від імені компанії. Мета — платні підписки партнерів Odoo
на алерти «твій стек зламався на новій версії», а безкоштовний публічний індекс є каналом.

## Сервер

4 vCPU / 8 GB RAM / 80 GB disk. Усі служби локальні, зовнішніх платних сервісів немає.

RAM: ОС+Docker 0.6 + Postgres 1.5 + 2×2.0 Odoo-раннери + 0.5 інше = запас ~1.4 GB.
**Рівно два воркери. Третій викличе OOM.** Swap 4 GB обов'язковий.

Диск: ОС+Docker 10 + образи odoo 9 + чекаути OCA 6 + Postgres 12 + логи 3 + сайт 1 ≈ 41 GB.
У вересні додається 20.0 — тоді прибрати чекаути 16.0/17.0.

## Домен: план перенесення

Стан на 18.08.2026:
- `allservices.one` → A `65.21.189.197`, **AAAA вказує на мережу OVH** (інший хост!),
  на 443 невалідний сертификат. Тобто там уже щось стоїть.
- Рішення власника: **наявний ресурс переїжджає на субдомен, апекс віддаємо цьому проєкту.**

Порядок (деталі й готові блоки — у `Caddyfile`):
1. Дізнатися, що саме зараз слухає 80/443 (`bin/preflight.sh`), і зберегти його конфіг.
2. **Розібратися з AAAA.** Якщо IPv6 вказує на інший сервер — або видалити AAAA, або
   переставити на IPv6 цього сервера. Інакше Let's Encrypt піде по IPv6 і сертификат не видасть.
   Це найчастіша причина «чомусь не працює HTTPS» у цій конфігурації.
3. Додати A (і AAAA, якщо є) для субдомену наявного ресурсу → цей же сервер.
4. Наявний веб-сервер перевести на `127.0.0.1:8080`, звільнити 80/443.
5. Підняти Caddy: апекс → новий статичний сайт, субдомен → `reverse_proxy 127.0.0.1:8080`.
6. Старі шляхи апексу → **301** на субдомен, інакше поламаються зовнішні посилання й інтеграції.
7. Перевірити обидва хости зовні до того, як прибирати старий конфіг.

Ім'я хоста не має містити «odoo» — обмеження товарного знаку.

## Git-потік

Репозиторій: **https://github.com/deasonsv/modules** (клонується в `/srv/modidx`).
Робоче правило: **сервер комітить свої правки, власник пулить у себе на Mac.**
Перед роботою — `git pull --rebase`; після робочих правок — коміт із осмисленим
повідомленням і `git push`. Деталі й deploy key — у `GIT.md`.

**Ніколи не комітити:** `.env` (пароль Postgres), `var/` (чекаути, логи, згенерований сайт,
бекапи), `pf.txt` (вивід preflight з IP і структурою сервера). Усе це вже в `.gitignore`.

## Що вже готове в цьому репозиторії

```
bin/preflight.sh     тільки читає; запускати першим
bin/bootstrap.sh     docker, swap, теки, postgres, схема, шаблонні БД (ідемпотентний)
bin/mktemplate.sh    шаблонна БД з установленим base на серію
bin/sync_repos.sh    чекаути OCA + плоский пул адонів симлінками
bin/maint.sh         нічне: прибирання, бекап, goaccess, healthcheck
bin/notify.py        SMTP через особисту скриньку (не піднімати свій MTA)
indexer/schema.sql   таблиці + черга задач у Postgres
indexer/harvest.py   зріз OCA лише через git — ПЕРЕВІРЕНО, дав цифри вище
indexer/enqueue.py   ставить у чергу нове й змінене
indexer/runner.py    воркер: БД з шаблону → docker run odoo -i → класифікація
indexer/classify.py  класифікатор причин падіння — протестований на 10 типових логах
indexer/export.py    генератор статики й датасету, без Node і Hugo
docker-compose.yml   Postgres (tuned) + Caddy
systemd/             юніти й таймери
```

Синтаксис усіх скриптів перевірено. **На реальному сервері ще нічого не запускалося** —
`runner.py` і `export.py` не проходили живого прогону. Очікувати правок.

## Архітектурні рішення — не змінювати без причини

| Рішення | Причина |
|---|---|
| Черга в Postgres, `FOR UPDATE SKIP LOCKED` | нуль додаткових служб; Redis тут не потрібен |
| `CREATE DATABASE … TEMPLATE tmpl_XX` | 1–2 с замість 30–60 с на установку `base` |
| Postgres `fsync=off`, `synchronous_commit=off` | БД прогонів одноразові; **тільки для цієї БД** |
| Батчі по 8 із бісекцією при падінні | виграш 5–8× на першому масовому проході |
| Плоский пул адонів симлінками | один `--addons-path`, міжрепозиторні залежності резолвяться |
| Статика на Python, без Hugo/Node | менше залежностей, нуль ресурсу на слабкій машині |
| Пошук у браузері по одному JSON | нуль серверних ресурсів |
| GoAccess по логах раз на годину | нуль постійної памʼяті замість Umami/Plausible |
| Датасет у git | offsite-бекап безкоштовно і водночас те, що цитують LLM |

## Найважливіший файл — `indexer/classify.py`

Якщо не відділяти «на машині немає python-пакета» від «модуль несумісний з версією» —
статистика буде брехливою, і весь проєкт нічого не вартий. Статуси `env` і `dep` **не**
зараховуються модулю як несумісність. Це навмисно і має бути описано на сторінці методології.

## Порядок робіт

**Сесія 1 — сервер живий**
1. `bash bin/preflight.sh > pf.txt` — подивитися порти, cgroup, місце, DNS, чи є конфлікт.
2. Розібратися з наявним ресурсом на 80/443 і з AAAA-записом.
3. `ROOT=/srv/modidx bash bin/bootstrap.sh`
4. `python3 indexer/harvest.py` — має відтворити цифри вище (±дельта за кілька днів).
5. Caddy на апексі з простою сторінкою «1 103 модулі на 19.0, 0 на 20.0» — уже публічна цінність.

**Сесія 2 — прогони**
6. `bash bin/sync_repos.sh` (~6 GB, 10–20 хв)
7. `bin/mktemplate.sh 19.0` і `18.0`
8. `python3 indexer/enqueue.py`, потім **один** `BATCH=1 python3 indexer/runner.py` вручну:
   переконатися, що модуль реально ставиться і лог парситься. Тільки після цього — systemd і BATCH=8.
9. Виміряти реальний час одного прогону і перерахувати пропускну здатність.

**Сесія 3 — сайт і публікація**
10. `python3 indexer/export.py`, перевірити сторінки модулів і `llms.txt`.
11. Датасет у git-репозиторій, сторінка методології.
12. Звіт «63% модулів OCA не перенесено на 19.0» → OCA GitHub Discussions, форум Odoo, r/Odoo, LinkedIn.

**Вересень**
13. 24-го: гілка 20.0 у харнес того ж дня, зріз за 72 години, табло міграції на головну.

## Чого не робити

- **Не піднімати третій воркер** на 8 GB.
- **Не піднімати власний MTA** — листи підуть у спам, домен постраждає.
- **Не робити масову розсилку** до налаштування SPF/DKIM/DMARC на `allservices.one`.
- **Не публікувати оцінки якості вендорів** — тільки факт прогону з логом і датою.
- **Не ставити «odoo» в ім'я хоста.**
- **Не втрачати старі URL** наявного ресурсу без 301.
- **Не міняти tuned-налаштування Postgres** на бази, дані яких шкода.
